> 类型标签：**推理档调优** · 现象：提升推理档（`effort`）后，整体分数上升，但**某一类"重编排"任务反而表现更差**——推理档并非单调增益。

## ① 元信息卡

| 字段 | 值 |
|---|---|
| 数据集 | AutomationBench v1.0.6（公开集，6 域 × 100 = 600 任务） |
| case_id / 任务名 | 推理档提升导致的域级退化（effort ↑ → 编排类任务退化；本实例落在 sales 域） |
| 所属域 / 任务类型 | sales 域 100 任务；任务形态：跨应用编排（docusign、linkedin、chatgpt、zoom）、选择判定（negative/priority selection）、多跳查找 |
| 被测模型 | deepseek-flash / effort=max（论文协议档） |
| 关键运行参数 | max: temperature=1.0, top_p=0.95, reasoning_effort=max, toolset=api, max_steps=50 |
| 基线 / 对照组 | deepseek-flash / effort=default（未下发 temperature、top_p、reasoning_effort） |
| 运行日期 | 基线 2026-10-09 / max 2026-10-10 |
| 严重度 | P1 显著（拉低整体通过率，且揭示"推理档越高越好"的直觉错误） |
| 标签 | `#推理档调优` `#非单调增益` `#步数耗尽` `#过度验证` `#串行化` `#采样噪声` `#跨应用编排` |

## ② 摘要（TL;DR）

- **现象**：把推理档从 default 提到 max（并套用论文协议 temperature=1.0 / top_p=0.95）后，整体通过率 +3.5pp（46.3%→49.8%），但 **sales 域逆势下降 44%→40%**，撞 50 步上限任务由 9 增至 19；同时 support 域反升 +14pp。推理档的影响**随任务形态而分化**。
- **根因**：`reasoning_effort=max` 使模型操作风格从"一轮并行打包多个调用"转为"做一步、验一步"的串行谨慎模式，单位工作量消耗步数膨胀；对"重操作编排类"任务（链长、跨多应用）杀伤最大，叠加 temperature=1.0 的采样噪声共同挤爆步数预算。
- **影响**：sales 域 12 个任务 PASS→FAIL（8 个反向翻转，净 −4）。揭示"提升推理档 = 全面提升"是错误假设；对重编排类任务，推理档提升需配合预算调整。

## ④ 证据链

**相同任务在两种推理档下的工具调用密度对比**（同一模型、同一任务、不同档）

| 任务 | 档位 | 轮次 | 工具调用总数 | 调用/轮 | 结果 |
|---|---|---|---|---|---|
| docusign_contract_send | default | 42 | 162 | **3.9** | PASS |
| docusign_contract_send | max | 50 | **111** | **2.2** | FAIL（撞限，score 0.909） |
| meeting_action_items | default | 8 | 20 | 2.5 | PASS |
| meeting_action_items | max | 24 | 48 | 2.0 | FAIL（score 0.765） |
| apply_project_label | default | 14 | 41 | 2.9 | PASS |
| apply_project_label | max | 26 | 70 | 2.7 | FAIL（score 0.714） |

**关键推断证据**：`docusign_contract_send` 在 max 档下**总工具调用数反而更少（111 < 162）**，但轮次更多（50 > 42）——证明不是"做了更多事"，而是**同样的工作量被拆散到更多轮次**，即行为从并行批量转为串行验证。其末条消息停在 "Let me verify the Salesforce opportunity update was saved"，典型"验证前预算耗尽"。

**Token 用量对比（全量 600 任务）**

| 指标 | default | max | 变化 |
|---|---|---|---|
| 输入 token | 7.61 亿 | 10.10 亿 | +33% |
| 输出 token | 1950 万 | 3715 万 | **+90%** |
| 总 token | 7.80 亿 | 10.47 亿 | +34% |

**终态快照**：max 档下 sales 域多数失败任务的最后一步仍是"读取/验证"动作，而非"执行/提交"，即动作序列被验证步骤截断。

## ⑤ 根因分析（分层）

**因子贡献度排序**：模型行为串行化 > 步数预算刚性（harness） > 采样随机性（temperature=1.0）

| 层级 | 归因 | 支撑证据 |
|---|---|---|
| 模型层（主因） | `reasoning_effort=max` 使模型决策更谨慎，放弃一轮多调的并行风格，改为"执行—验证—再执行"的串行节奏，导致单位任务的轮次膨胀 | ④ 中 3 个任务的调用/轮从 2.5–3.9 降至 2.0–2.7，且 docusign 总调用数下降而轮次上升 |
| Harness 层（放大器） | 协议固定 `max_steps=50`，串行化后步数预算被提前耗尽；被"饿死"的 5 个任务旧步数本就在 26–42 的高位 | ③ 中 5 个新增撞限的 PASS 任务 |
| 数据层（次因） | sales 域天然偏"重操作编排"（需跨 docusign/linkedin/chatgpt/zoom 多应用），对轮次消耗敏感；相较 support 域（偏单点判读）更易受串行化伤害 | 新增撞限任务约 10/16 为跨应用编排类 |
| 采样层（噪声） | temperature=1.0 引入随机性，7 个"未撞限仍失败"任务的 partial 分落在 0.71–0.91，含采样波动成分 | ③ 下 7 个任务列表 |

## ⑥ 影响评估

- **是否代表一类问题**：是。凡"编排链长、需跨多应用、动作步骤多"的任务（sales、部分 operations）在固定步数上限下都会受"推理档升高 → 串行化 → 预算耗尽"影响，这与 support 域（+14pp）形成鲜明对照，证明推理档收益随任务形态而变。
- **波及范围**：sales 域 100 任务中 12 个受影响（12%）；全量层面 max 档共 72 个任务撞限（baseline 53 个），其中"原 PASS 被饿死"的任务构成净损。
- **严重度定级理由**：未阻断评测流程，但拉低整体分数并扭曲"推理档越高越好"的直觉，故定 P1。

## ⑦ 经验沉淀

**可复用结论**：

- **推理档提升非单调增益**：更深的推理可能改变模型的操作风格（并行→串行），在固定步数上限下对"重编排类"任务产生负收益，不能假设 `effort` 越高分数越高。
- **"调用密度"是诊断串行化的有效指标**：任务总调用数变化不大但轮次显著增加、或调用/轮下降时，即可判定为串行化导致的预算耗尽，而非能力不足。
- **聚合分数必须下钻到域/任务类型**：整体通过率 +3.5pp 会掩盖 sales 域 −4pp 的退化，只看总分必然得出错误结论。

**避坑 Checklist**：

- [ ] 提升推理档后，必须按**域**和**任务类型**拆解对比，禁止只看总分。
- [ ] 检查"撞步数上限任务数"是否上升；若是，优先怀疑行为串行化而非模型变弱。
- [ ] 对比同一任务的"轮次 / 工具调用总数 / 调用密度"三项，判定是否串行化。

## ⑧ 对数据集设计的启发

- **任务设计**：本 case 暴露"重编排类任务对步数预算极度敏感"这一隐藏难度维度。数据集应为每个任务**标注"最小可行步数 / 预算敏感度"**，使测评方能区分"任务太难"与"任务太长"；过长编排链任务可拆分或标记为"高压预算任务"。
- **断言设计（含计分与部分信用）**：现有断言**全部后置**（校验末尾产出），被截断即全零，无法区分"做了但被截断"与"完全没做"。建议为长任务**引入过程性/中间断言**（如"是否已正确解析层级""是否已换算汇率"）以恢复可观测性并产生部分信用；计分上应对"撞限失败"与"真失败"**分列统计**，避免预算问题混入同一通过率。
- **难度与分布（含可复现性）**：应公布每个任务的**步数分布**与**运行间方差**，识别并标注"贴边任务"（如参考配置下 41–49 步者）。`temperature=1.0` 下贴边任务会出现 1.00↔0.00 跳变，故需**固定随机种子**或对贴边任务**多次重复取均值**，避免把高方差任务当作能力信号。

## ⑨ 对模型推理/训练的优化思考

- **能力缺口**：高推理档下模型**丧失"并行打包无依赖调用"的规划能力**，退化为逐条串行验证——"更聪明反而更低效"。缺的不是智商，是**预算感知与动作编排效率**。
- **推理期可优化**：在 system prompt 显式鼓励"对**无数据依赖**的调用应在同一轮并行发起"；注入预算感知提示（"你有 N 步预算，请优先执行有副作用/不可逆的最终动作，验证次之"）；适当降温以缓解温度引入的近失任务抖动。
- **需训练解决**：训练**预算感知策略**（优先提交有副作用动作，而非把验证前置）；在 RL 奖励中引入**步数效率项**（同样正确、步数更少者得分更高）；对"重编排"轨迹做专项 SFT，示范一轮多调的并行风格。

## ⑩ 对 agent harness 的优化思考

- **工具接口与发现**：`api` toolset 直连 47 个工具且无搜索机制，模型只能在"工具海洋"中反复试探（单任务曾达 246 次调用），是串行化与预算耗尽的直接诱因。建议提供**元工具发现**（search/execute 模式）或工具清单摘要，把预算留给真正的业务动作。
- **循环与预算控制**：`max_steps=50` 对"重编排类"任务偏紧且**刚性无过渡**。建议按任务类型设**差异化步数上限**，或引入"步数-完成度"**软约束**（临近上限时提示模型收尾）。
- **上下文与提示脚手架**：当前未在提示层引导"并行调用"与"预算感知"，模型在 max 档自发转为串行验证。建议注入**并行无依赖调用鼓励** + **预算感知提示**（先提交有副作用动作、后验证），直接抑制串行化。
