先看一组反差。

同一个 Codex + GPT-5.5，在 Terminal-Bench 上全对率 82%，换到 UC Berkeley RDI 新出的 Agent 基准 **Agents' Last Exam（ALE）** 的 Linux 子集 ALE-CLI 上，只剩 **25.2%**。这还不是最惨的：最难一档 Last-Exam，所有主流"外壳+底座"配置的平均全对率只有 **2.6%**，Claude Code、Grok CLI 等一排知名配置直接挂零。

2.6% 还是论文发布时的快照。到本文截稿（2026-09），官方实时榜单上的历史最好成绩也不过 **34.2%**——榜首已经从 GPT-5.5 换到了 GPT-6-Astra，涨的这 8 个百分点，还不够把 Last-Exam 档从"几乎全军覆没"里捞出来（该档最好成绩 13.2%）。

为什么？Terminal-Bench 考的是"把命令行的活干完"，ALE 考的是"**把一位真实专业人士交付过的项目原样重做一遍**"——在真实 Windows/Ubuntu 虚拟机里，用真实商业软件，从 ERP 全流程、CAD 仿真到临床数据管线。而且模型说自己做完了不算数：每道题的参考答案，在 agent 收工之后才被解密注入评分。

## 一、数据集身份证

一句话定位：**它测的不是模型答什么，而是"一位真专业人士的活，agent 能不能原样交付"**。

| 字段 | 内容 |
| --- | --- |
| 出题方 | UC Berkeley RDI × RDI Foundation，300+ 行业专家（顾问委员会含 Berkeley 多院系教授） |
| 领域口径 | 按美国联邦职业分类 O*NET / SOC 2018：13 个行业集群 × 55 个子领域，55 个目标子行业已全覆盖 |
| 规模 | 官网已收录 1,500+ 任务工作流（论文发表时为 960 工作流 / 1,490 任务实例），官方目标 5,000 题；公开评测集 152 题，另有 Linux-only 子集 ALE-CLI（105 题） |
| 任务结构 | 可执行 `main.py`：`load()` 声明题面 → `start()` 置初始态 → `evaluate()` 对产物评分 [0,1] |

## 二、运作机制三件套

ALE 的可信度不靠玄学，靠三个硬机制：**考题是挖出来的、答案是后置注入的、考场是真机器**。

### 机制一：考题不是出出来的，是挖出来的

大多数基准的题由策展人设计，ALE 的题来自从业者**已经交付过的真实项目**：专家通过提交门户上传自己过去花数天到数周完成的工作，拆成五要素（自然语言描述、输入文件、目标软件、期望交付物、评估规格）。

但"挖出来"不等于"直接用"——每道题要过**五道门**：专家招募与选题 → 提交与迭代精修 → 会议式首轮评审（major/minor revision、accept，淘汰不合格提案）→ 工程团队落地实现（容器化软件、编码评估逻辑、试跑）→ 专家委员会终审 QC（参考答案是否正确、评估边界是否过宽过窄、上下文是否足够解题）。一道题能上市，等于过了一轮 peer review。

### 机制二：答案后置注入 + gate-and-score

任务规范是一个 `main.py`，三个生命周期函数把"出题"和"判卷"物理隔开：`start()` 只把输入数据铺进虚拟机；**hidden reference 在 agent 停手之后才被 stage（解密）注入**，运行期间答案不在机器上，无从泄漏。`evaluate()` 拿 agent 留下的产物对照 reference，返回 [0,1]。

评分模式刻意多样，因为交付物本身五花八门——工作簿字段、3D 网格、渲染截图、游戏世界状态、自由文本报告：

- **gate-and-score**（最常见）：硬前置门不过直接 0 分。论文的招牌例子是 manufacturing/gcode——先过 PowerMill 碰撞/过切检查，再按参考 STL 的表面距离给几何相似度分；**刀具路径会撞坏工件，模型再像也是 0 分**，从设计上堵死 reward hacking；
- 结构化数值按（字段，值，容差）清单逐项给分；几何按表面距离分带给分；
- **默认禁 LLM-judge**：交付物能化成字节、字段、几何或可执行行为的，评分代码必须操作这些信号。规则写得很硬——"问 GPT-4 结果对不对"的任务在 QC 阶段直接打回。理由有三：judge 模型会漂移、宽泛提问分不出"接近对"和"对"、确定性判分任何人可离线复跑。极少数（渲染/游戏画面）确需视觉 judge 的，也只允许**证据锚定的窄是非题**，分数由代码聚合。

### 机制三：把 CLI Agent 抬上桌面

真实职业工作要**同时**用终端和屏幕。论文把 agent 能力拆成五层：Brain（推理）、Eyes（看屏）、Body（编排）、Hands（工具）、Feet（运行时）——传统 CLI-agent 缺 Eyes，GUI-agent 缺 Hands 和 Feet。所以 ALE 的评测对象是 **Generalist CUA-agent（GCUA）**：五层齐全。

主流 harness 都是 CLI 原生，ALE 用一个**统一跨 OS 的 CUA MCP bridge** 把它们抬到桌面：截图、点击、键入、滚动等 14 个桌面动作作为普通工具注入 agent 的动作循环，一个底座模型在同一个循环里同时消化 shell 输出和视觉反馈。

## 三、一道题解剖

机制说完了，拆一道题：`business_finance/odoo`——公开任务库里最完整的端到端业务流之一。选它不是因为它官方挂名门面，而是因为 ALE 的全部核心机制（真实商业软件、链式硬约束、防作弊标签、gate-and-score）在它身上集齐，且题面与评分口径完全公开可复查。

### 第一拍：题面长什么样

环境是一台预装 **Odoo 19 + PostgreSQL 17** 的虚拟机，agent 要独立跑完一条供应链全流程（摘要）：配置币种与锁定汇率（1 EUR = 1.20 USD / 1 CNY = 0.125 USD）、FIFO 自动估值、两仓两套路由；建 9 个往来单位和产品主数据（精确编码，含两级 BoM）；下销售订单并触发 **FP-1000 走 MTO→制造、ACC-900 走代发（dropship）**；五张采购单；入库 + landed cost 按当前成本拆分；委外采办并逐个分配序列号；两级制造，中途**主动报废一个微控制器**制造缺料，要求自建补货 PO 恢复；部分交货 + backorder；EUR 开票两张（460/230）并收款；供应商账单核销；费用报销；最后**强制退货 SSK-0002 并开 200 EUR 红字发票**。全程关键单据必须打上 run tag `odoo_compact`。

一个熟练 ERP 操作员半天的工作量，压缩给 agent 独立完成。

### 第二拍：题目里的陷阱地图

| 陷阱 | 题目里的样子 | 踩中的后果 |
| --- | --- | --- |
| 链式依赖 ×12 | 配置→主数据→销售→采购→入库→委外→制造→交货→开票→账单→费用→退货，环环相扣 | 前面错一步，后面连锁歪，且无中间提示 |
| 路由分流 | FP-1000 走 MTO→制造，ACC-900 走代发直发客户；两仓分别是 2 步收货 / 3 步发货 | 路由配错，交货链整体卡死 |
| 强制缺料恢复 | 第 7 步设计要求 scrap 一个 RM-030 | 不主动建补货 PO 并走完全程，制造完不成 |
| 精确数字 | landed cost 拆分必须正好 60/40 USD；发票 460/230 EUR；红字 200 EUR | 差一点就是差，逐字段容差判定 |
| 序列号纪律 | SSK-0001..0003 / CS-0001..0003；被退的 SSK-0002 必须回到 My Co 库存 | 记错一个序列号，库存对不上 |
| run tag 防作弊 | 关键单据的可搜索字段（Reference/Notes 等）必须带 `odoo_compact` | 证明业务对象是这次跑出来的，不是预置数据 |

### 第三拍：正确的推理链

一个合格的"新员工"要走完 12 个阶段，核心链路是：

| # | 动作 | 避开的坑 |
| --- | --- | --- |
| 1 | 全局配置：币种、锁定汇率、FIFO 自动估值、两仓路由 | 后续所有金额与转移的前提 |
| 2 | 建主数据：9 个伙伴/产品精确编码 + 两级 BoM + 委外 BoM | 编码错则全链找不到料 |
| 3 | 建价目表、下销售单并确认 | 必须触发 MTO 与代发两条规则 |
| 4 | 五张采购单分币种下达 | 多币种 + 代发单混在一张清单里 |
| 5 | 2 步收货入库，建 landed cost（100 USD 运费按当前成本拆） | 拆分必须正好 60/40 |
| 6 | 委外：供料→收 SC-300→逐个分配序列号 | 漏供料则委外收不了货 |
| 7 | 两级制造；中途 scrap RM-030 → 自建补货 PO → 收货转移 → 续产 | 缺料恢复是题面写死的必做项 |
| 8 | 3 步交货：部分交 2 台 + backorder 1 台；ACC-900 代发直发 | backorder 与代发并行不乱 |
| 9 | 两张 EUR 发票（按交货量开票 460/230）并收款到 Paid | 开票时机绑定交货进度 |
| 10 | 全部 PO + 运费的供应商账单核销 | 与发票区分，别混 |
| 11 | 费用报销走完 提交→批准→入账→付款 四步 | 少一步状态就不对 |
| 12 | 退 SSK-0002 回 My Co 库存 + 开 200 EUR 红字发票并核销 | 只退 FP 部分，金额别含配件 |

任何一环掉链子，终局业务状态就不对，**没有中间反馈告诉你哪步错了**，唯一的纠错信号是自己回头查一遍的自觉。

### 第四拍：终局对账

agent 停手后，`evaluate()` 直接连数据库对账。先过三道**硬门**，任一触发直接 0 分：

- 变体数据库 `odoo_compact` 经 psql 不可达；
- 库存/会计/制造/landed-cost 关键表缺失；
- 任何带 run tag 的业务证据都找不到（即整个流程可能是预置数据冒充的）。

门过了之后，12 项检查**等权计分**，每项都是对终局状态的具体断言，代表性几条：landed cost 拆分恰好 `RM-010 = 60.00 / RM-020 = 40.00`；销售单 `FP-1000 x3 + ACC-900 x3` 处于 sale 状态；两张已付发票恰为 460/230 EUR；一张 200 EUR 已付红字发票；序列号库存 `SSK-0001..0003` 与委外 `CS-0001..0003` 逐一在册；终态库存 `My Co: FP-1000=1, RM-010=4, RM-020=7` 且退回的 SSK-0002 回到 My Co；一条 scrap 移动与一张对应补货 PO 配对存在。**满分 = 硬门全过 + 12 项全中**——11/12 也拿不到 pass。

这题最见出题功力的是 run tag 设计：它把"过程真实性"压缩成一个可检索的字段断言——不用看过程日志，一条 SQL 就能排除"用预置数据糊弄终态"的作弊路径，等于给"只考终态"的评分范式补了一块过程短板。

## 四、为什么难

官方对失败案例做了两层根因分类（对象：Claude Code + Opus 4.7 的失败跑，每条结论必须引用具体日志文件作为证据）：

- **Approach 类占 47%**：策略错误 30% + 中途放弃 17%——理解了领域，但路子错了或没做完就停；
- **Understanding 类占 31%**：领域知识缺口 25% + 编造数据 6%；
- **Execution 类占 22%**：输出格式错 10% + 实现缺陷 8% + GUI 交互失败 4%。

表象之下是三条结构性归因，每条都对应明确的出题设计：

| 归因 | 题目怎么设计 | 效果 |
| --- | --- | --- |
| **领域知识缺位** | 考题来自真实交付，考 PowerMill 仿真、Odoo 供应链、KiCad 布局——训练语料里这类深度工作流近乎空白 | agent 退回 ad-hoc 脚本，但交付物是软件内的业务状态/工程文件，脚本糊弄不过去 |
| **硬约束不可商量** | 序列号、run tag、精确金额、backorder——全是链式依赖上的具体断言 | "大概做对了"没有折扣，逐字段容差判定 |
| **长程无反馈** | 12 阶段流程、5 小时上限、$3–10/题 | 中途放弃成为第三大死因，试错成本极高 |

还有一条官方量化结论值得记住：固定外壳换底座，全对率波动 **18 个百分点**（Grok 4.3 的 5.3% 到 GPT-5.5 的 23.3%）；固定底座换外壳，只有 5–6 个百分点。**瓶颈在模型的领域知识与推理，不在外壳工程**——这和失败分类里 Understanding+Approach 占近八成完全互相印证。

而工具使用数据暴露了更尴尬的一层：34% 的公开任务指定图形软件为主工具，但几乎所有配置的 GUI 调用占比都远低于这个数——agent 在用 Bash 硬绕本该点界面干的活，绕不动的地方正是失分的地方。

## 五、冷思考

**盲区一：只考终局产物，过程分文不值。** 统一轨迹记录了每一步工具调用和观察，可回放可审计——但评分不看它。对 RL 训练这是特性：奖励只认交付物，路径自由；对能力归因这是噪声：你分不清"熟练操作"和"侥幸终态对"。run tag 补了一角（证明对象是这次跑的），但顺序、效率、操作合理性仍在评分视野之外。

**盲区二：确定性与覆盖面之间的取舍。** 1,500+ 个工作流里总有交付物天然不可字节化的（渲染画面、音乐制作、游戏复现），只能落到视觉 probe——虽然被约束成窄是非题，主观性和 judge 漂移只是被压制，没有被消灭。

**盲区三：复现门槛极高。** 每题 $3–10、最长 5 小时，独立复跑一次 152 题榜单是数百美元加数天机时；总池已超 1,500 个工作流、官方目标 5,000 题且持续增长（living benchmark），意味着跨期分数不可直接对比、公开子集与私有池的分布差永远存在。这既是严肃性的来源，也是社区独立验证的墙。

即便如此，ALE 最值得带走的仍是三个设计：

1. **hidden reference 后置注入**——把"答案不可泄漏"做成物理隔离而非信任假设；
2. **gate-and-score + 默认禁 LLM-judge**——确定性评分从单个断言升级成跨交付物类型的完整方法论；
3. **专家真实项目 + 五道 QC 门**——题源供给侧的 peer review，直接对标 GDPval 类基准最被诟病的人工评分依赖。
