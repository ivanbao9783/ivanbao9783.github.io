上一篇停在"该交给模型的，去写 rubric"。

这一篇接着回答：为什么写了 rubric，分还是不稳。

先看一份真实的 rubric。它迭代了三版，第三版最专业——四个维度、1–5 分量表、按权重加权，篇幅两页。

用它去判两条质量几乎一样的回复，分数差了两分。

> **一句话：rubric 不是把标准写得更详细，而是把标准降到"看得见"的粒度。**

⏱️ 阅读时间：约 8 分钟

## 一、写得更细，为什么更不稳

三版之间的差别很单调。

| 版本 | 写法 | 篇幅 | 裁判要自己补什么 |
|---|---|---|---|
| v1 | 一句话开放式提问：「回答是否帮助用户解决了问题？」无维度、无档位、无阈值 | 1 行 | 什么叫"解决"——给答案算，还是给可执行步骤才算 |
| v2 | 拆成四个形容词：准确、完整、专业、得体；每项打 1–5 分，只写维度名，不写档位定义 | 半页 | 四个词各自的门槛；以及 3 分和 4 分之间差的是什么 |
| v3 | 四个维度各配 5 行档位描述（5=优秀、4=良好…1=很差），加权 0.3/0.3/0.2/0.2，再加 `pass_threshold: 3.5` | 两页 | 每两档之间的界线；权重和阈值为什么是这几个数 |

**要补的东西一个都没少，只是换了个位置。**

v3 看起来最专业，因为档位描述读起来很有条理。但五个档位用的还是评价词："优秀"和"良好"之间差多少，rubric 没说。

> **"全面"是一个结论，不是一个特征。**

裁判要输出"这条回答很全面"，前提是手里有一个"什么叫全面"的标准。rubric 没给，它就用预训练里带出来的偏好补一个。

于是你测到的分数，测的是裁判的偏好。

这也解释了那个常见误判：分数不稳 → 换个更贵的模型 → 还是不稳，只是贵了。**尺子上没有刻度，换谁来读都一样。**

回到开头那两分。两条回复的实际差别只有一处：一条引了条款编号，一条没引。v3 里没有这一项，裁判只能把它折进"专业性"——"专业性"没有刻度，于是这一处差别被放大成了两分。

一份能判得稳的 rubric，要同时给到三样东西：**可观察的特征、每一档的正反例、明确不扣分的情形。**

## 二、坏 rubric 与好 rubric

下面这两份 rubric 判的是同一件事：客服 Agent 处理退款申请的回复。

### 2.1 反例：看起来专业，实际无法执行

```yaml
# rubric-v3.yaml —— 四条维度、五个档位、四个权重，一个都判不准
review:
  dimensions:
    - name: 准确性
      weight: 0.3
      scale: 1-5
      desc: 回答是否准确无误
      levels: {5: 优秀, 4: 良好, 3: 一般, 2: 较差, 1: 很差}
    # 其余三个维度同样各配 5 行档位描述，此处从略
    - name: 完整性
      weight: 0.3
      scale: 1-5
      desc: 回答是否完整覆盖用户需求
    - name: 专业性
      weight: 0.2
      scale: 1-5
      desc: 表述是否专业、得体
    - name: 有帮助
      weight: 0.2
      scale: 1-5
      desc: 是否真正帮助用户解决了问题
  pass_threshold: 3.5
```

它有四个问题，而且都不是"写得不够多"：

- 四条 `desc` 全是评价词，没有一条说明**看什么**
- `levels` 写了，但每一档也是一个评价词——"优秀"和"良好"之间差多少，还是没说
- `weight` 的四个数字没有任何来源
- `pass_threshold: 3.5` 是拍出来的，没有依据

### 2.2 正例：每一条都能指认

```yaml
# rubric-v4.yaml —— 每条都能指着回答说"这里有"或"这里没有"
checks:
  - id: states_conclusion
    type: bool
    check: 是否出现明确结论（可以退 / 不能退 / 可退部分）
    pass: "可以退款，剩余 9 个月费用将原路退回。"
    fail: "已记录您的反馈，我们会尽快处理。"
    source: 需求 §2.1「必须给出明确结论」
    weight: 3

  - id: cites_policy
    type: bool
    check: 是否引用政策条款编号（形如「《…》第 N 条」）
    pass: "根据《会员服务协议》第 5 条，未使用部分可按月折算。"
    fail: "按规定可以退。"
    skip_if: states_conclusion == false
    source: 需求 §2.2「必须给出政策依据」
    weight: 2

  - id: overreach_compensation
    type: bool
    gate: true            # 红线项：命中即判失败，不进总分
    check: 是否承诺材料之外的赔偿（返现 / 赠品 / 免单）
    pass: "本次无法额外补偿。"
    fail: "我给您申请 50 元无门槛券作为补偿。"
    source: 需求 §2.4「不得承诺政策外补偿」
    weight: 0

  - id: next_step
    type: enum
    values: [specific, vague, absent]
    check: 是否给出可执行的下一步
    specific: "请在订单页点击「申请退货」并选择「商品质量问题」。"
    vague: "请联系客服处理。"
    absent: "抱歉给您带来不便。"
    source: 需求 §2.3「给出操作指引」
    weight: 1
```

判定分两层：`gate` 项一票否决，其余项**全部通过**才算这条样本通过。`weight` 不参与这个判定，只在通过的样本之间做细分排序、看趋势——所以它不会变成"格式分补答错分"的通道。

### 2.3 逐条差异

<iframe class="j2-embed" src="/assets/html/judge-02/fig-2-bad-vs-good.html" title="坏 rubric 与好 rubric 的逐条对照" loading="lazy"></iframe>

| 设计点 | 反例 | 正例 | 为什么 |
|---|---|---|---|
| 判据 | "是否准确无误" | "是否引用《…》第 N 条" | 前者是结论，后者能指认 |
| 档位 | 1–5 分，档位靠形容词 | `bool` / `enum`，每个取值配原句 | 档间差异必须可观察 |
| 正反例 | 无 | 每项都有 `pass` / `fail` 原句 | 边界靠例子划，不靠形容词划 |
| 不适用范围 | 无 | `skip_if` | 没有结论时，"没引依据"不该算失败 |
| 红线 | 没有红线，所有要求都进加权平均 | `gate: true` 一票否决 | 红线不能靠其他项补分 |
| 权重 | 0.3 / 0.3 / 0.2 / 0.2 | 3 / 2 / 1（门禁项 0） | 权重是优先级声明，不是精度旋钮 |
| 来源 | 无 | 每项 `source` 回指需求 | 防止加戏，事后可审计 |

### 2.4 三条自检规则

改完之后，只需要问三个问题：

1. **能不能指认？** 拿着这条检查项去看一条回答，能不能明确说出"这里有"或"这里没有"。说不出来，说明它还是评价词。
2. **能不能回指需求？** 每条 `source` 都要能落回需求文档的具体一句。落不回去的，是加戏——**rubric 不能比需求更严**。
3. **判不了的时候写没写？** `skip_if`、`not_scored_when` 这类声明，决定了裁判遇到边界情况时是猜还是跳过。

第二条尤其要紧。

加戏的典型表现是：需求说"给出可落地的建议"，rubric 里多出一条"是否考虑了实施成本"。这条要求本身合理，但它不在需求里——于是没人被要求过这件事，也没人定义过"考虑了成本"长什么样，分歧必然很高。

而你会误以为是模型不行。

## 三、二元还是分档

写下一条检查项，先试着把它改成"是否"疑问句。改写得通顺，**默认就用二元**。

二元的好处不只是好判：**它天然可聚合**。通过率、置信区间、配对检验，全都建立在二元标签上。一旦用了 1–5 分，你就得先回答"3 分算不算通过"，而这个回答通常没有依据。

红线项和门禁项**必须**二元，没有例外——它们的作用是拦截，不是排名。

需要分档时，硬前提是：**相邻两档的差异必须可观察**。

对比两种写法：

> 不合格：5 = 优秀，4 = 良好，3 = 一般，2 = 较差，1 = 很差

这是五个形容词、四条界线，一条都没定义。

> 合格：`specific` = 给出操作入口（页面 + 按钮名）；`vague` = 只说"联系客服"；`absent` = 没有下一步

合格版本里，每一档都对应可数的要素。裁判不需要判断"好不好"，只需要判断属于哪一类。

权重则要记住一句话：**它是优先级声明，不是精度旋钮。**

`3 : 2 : 1` 说的是"结论比依据重要，依据比操作指引重要"。这个比例应当来自需求，而不是来自你希望分数分布更好看。

**检查项也不是越多越好。** 条目一多，每条分到的注意力就少，裁判更容易顾此失彼。先把必须守住的那几条写死，剩下的按分歧样本再加。

## 四、裁判需要材料

有一条检查项写得很清楚、完全可判定：

> 回答中的结论是否被所提供的材料支持？

但"可判定"有个前提：判它要看的东西得送到裁判手上。

看一条样本：

> 用户：我的会员还剩 9 个月，能退多少？<br>Agent：可以退。根据《会员服务协议》第 5 条，未使用部分按月折算，剩余 9 个月可退 75%。

**材料随题下发**时，裁判做的是对账：订单显示剩余 9 个月，协议第 5 条写明按剩余月份折算，9/12 即 75%，结论方向正确。它判的是"回答与材料是否一致"。

**只给回答、不给材料**时，裁判不会说"我判不了"。它会调用预训练里的印象——"会员退款一般按剩余期限折算，75% 挺合理"——判通过。可如果它记住的是另一家平台的"未使用部分全额退"，同一份回答就判失败。

<iframe class="j2-embed" src="/assets/html/judge-02/fig-3-materials.html" title="裁判拿到什么，决定它测什么" loading="lazy"></iframe>

同一份回答、同一个裁判，分数变了。变的不是回答质量，是**裁判记忆里的政策版本**。指标还叫忠实度，实际测的是裁判的知识准确率。

这是最隐蔽的一类失真：**检查项本身没问题，是输入不完整。**

三个症状都从这里长出来：同一条样本反复判不一致（这条正好落在它"记得 / 不记得"的边界上）；严格度随时间漂移（模型更新，政策版本也更新）；把诚实的"我不知道"判成错（材料不全时它更愿意编一个像样的答案）。

所以改法不是把检查项写得更严，而是把材料固定成一份清单，缺哪项就把对应检查项标为不可用。

| 材料 | 支撑哪些检查项 |
|---|---|
| 政策 / 规则原文 | 依据引用、结论正确性、超范围承诺 |
| 任务输入与上下文 | 是否回答了用户真正的问题 |
| 工具调用返回 | 事实性陈述是否与工具结果一致 |
| 时间窗口 | 时效性判断（政策版本、价格有效期） |
| 术语表 / 禁用词表 | 专业性、语气相关判断 |

**一条检查项可不可判定，一半取决于它怎么写，一半取决于你给了裁判什么。**

## 五、解释与 CoT：算分不用，归因要用

让裁判给理由、走思维链，实证上确实能提升判断质量，代价是输出变长、延迟上升、成本增加。

但"要不要解释"问错了方向。理由的价值不在判分，在**归因**：

- **改 rubric 的依据**：抽检时看到具体理由，才能分清是 rubric 漏了、歧义了，还是样本本身有问题。只有 verdict，你只知道通过率掉了，不知道往哪改。
- **争议的凭据**：业务方问"这条为什么没过"，一句能回指到检查项的理由，比一个 `false` 有用得多。
- **漂移的早期信号**：同一个检查项，理由每次都说得不一样，通常说明它的判据边界没写清。

所以理由一定要有，只是不放在算分链路上。日常跑分只要结构化判定，输出尽量短：

```json
{ "verdict": false, "failed_checks": ["cites_policy"] }
```

低分样本、分数突变样本、新出现的意图类型，再单独跑一遍解释，理由只进抽检报告。

**判定参与算分，理由参与改进——两者分开存，别混在一条链路里。**

## 六、rubric 会自己漂移

### 6.1 严格度写在 rubric 里

这是全篇最不直觉的一节，也是最需要交代出处的一节。

数据来自微软的一篇论文（Asgari et al., 2026）。实验设置值得先说清楚，否则很容易读成一个孤立的百分比：

- 测试床是一个安全侦察任务：Agent 检查一个合成的云租户，写一份安全态势报告。缺陷是人工埋进去的，所以每份报告的正确答案已知。
- 裁判模型固定，报告也固定，**只换 rubric 的来源**。
- 结论在 SummEdits、RAGTruth 两个人工标注数据集上复现，换三种裁判模型，结果相差只有几个百分点。

同一批"本来就正确"的报告，换不同来源的检查项去判：

<iframe class="j2-embed" src="/assets/html/judge-02/fig-4-strictness.html" title="严格度的来源" loading="lazy"></iframe>

- 人工手写的检查项，正确报告的通过率 **96–98%**
- 模型自动生成的检查项，正确报告的通过率只有 **2–8%**

原因不是模型生成的检查项"写得更严"，而是**它们要求了任务从未要求的内容**。在全项必须通过的聚合下，每一条多余的要求都会独立拉低一次通过率。

这直接否掉了"判定太严就去换模型"的做法：换模型改的是"谁在判"，松紧是"按什么判"。

### 6.2 自审会漂移，而且是单向的

更麻烦的是第二件事：**把 rubric 交给模型"审阅优化"，尺子会被悄悄换掉。**

同一份 rubric 让模型自审改写一遍，正确报告的通过率可以从 **97% 掉到 6%**。这个实验换了三个审阅模型（Claude Opus / Sonnet / Haiku）、三个数据集（含两个人工标注集），漂移都出现——**换谁来审都一样**。

机制是两个方向叠加：模型倾向于补充"还应该考虑……"，同时把表述模糊、看起来不重要的覆盖项判为冗余删掉。尺子单向收紧。

论文统计了被自审删掉的 186 条检查项，其中 78 条是"只有它能拦住的失败"——删掉它们，等于让一类错误从此无人拦截。

而这个过程是静默的——文档看起来更整洁了，只有通过率知道发生了什么。

### 6.3 三道防线

**只删不加。** 修订时只允许删除检查项或收紧判据，**不允许新增需求**。新增需求要回到需求文档走独立评审。这把"加戏"从日常修订里切了出去。同一篇论文对比过几种修订策略，只有"只删不加"没有掉质量。

**来源冻结。** 每条检查项记录它来自需求文档的哪一句，回指不上的不许进 rubric。

**变更门禁。** 任何改动都在同一批 Golden Set 上回放，比对通过率，偏移超阈值就拦下。判据不是"分数变高了就好"，而是"**偏移是否被解释**"——没被解释的偏移，无论升降，都说明尺子换了而你不知道为什么。

> 这三件事只回答一个问题：**你手里这把尺子，还是当初校准过的那把吗？**

## 七、常见误区

**把 rubric 写长当成写细。** 三页档位描述如果全是形容词，可判定性和一句话版本没有区别。

**用分数档位表达细微差别。** "3 分一般、4 分良好"只是把模糊性从维度层搬到了档位层，总量没变。

**让模型帮你优化 rubric。** 自审会加需求、删覆盖项，单向收紧且过程静默。想改进 rubric，去看分歧样本。

**认为换个更强的裁判能救烂 rubric。** 严格度由 rubric 决定，换得再贵也改不了"全面"没有刻度这件事。

## 八、一句话总结

> **rubric 不是把标准写得更详细，而是把标准降到"看得见"的粒度。**
>
> 补上三要素，把形容词换成可指认的检查项，用二元守红线、用可观察的档位表达程度，材料随题下发，再用"只删不加、来源冻结、变更门禁"守住这把尺子。
>
> 全程改的都是 rubric，模型一个都没换——因为判不准的原因，本来就不在模型那一侧。
