Agent 时代，评测不可能只靠人肉：一条任务几十步工具调用、几万字轨迹，样本按百条算、迭代按天走。纯人工评测在成本和节奏上都已经出局，于是裁判模型成了标配。

常见的做法是这样：用另一个模型充当裁判，去读 Agent 的整段输入和输出，基于一句笼统的提示词——"分析 Agent 轨迹并根据 Agent 表现和回答质量打 1-5 分"——给出最终判断。

问题不在流程，而在裁判的处境：**它从未拿到一份清晰的"失败的定义"。**

一份没有失败定义的评分标准，裁判只能自己补上一个默认值：**读起来像不像一个高质量的回答？** 于是答非所问的拿高分，把政策条款原样复述、不给结论的拿高分，承诺了政策里没有的赔偿也拿高分——它们读起来都很像。

这也解释了为什么有些评测团队的流程越做越多，加测试集、加评分维度、加裁判，问题却一个都没少：**尺子的刻度还是裁判自补的那个默认值，测多少次都是同一个答案。**

不是裁判不够聪明，也不是 prompt 不够狠、流程不够多。

> **一句话：judge 不是从 prompt 开始的，而是从"对失败的定义"开始的。**

## 一、先定义失败：从读数据到失败分类法

### 1.1 为什么"读数据"不可外包

Hamel Husain 在《Your AI Product Needs Evals》里把这件事讲得最直白：评测的第一道门槛不是写 prompt，而是**读数据**——真实的用户输入、真实的轨迹、真实的失败长什么样。

他给这条纪律的表述是：读数据不可外包，也不可跳过。你可以让别人帮你写脚本、搭流水线，但"你的产品在什么情况下会失败"这个判断，只能由做这个产品的人自己看样本得出（[来源](https://hamel.dev/blog/posts/evals/)）。

同一个起点在 Arize 的 judge 指南里也是开篇：先想清楚"要抓的失败是什么"，再决定用哪些 evaluator（[来源](https://arize.com/guides/llm-as-a-judge/)）。

原因不难理解。回到开头那句话：裁判需要一个刻度。

你不给它，它就自己造一个；你想给它一个，就必须先能说清"什么算错"。

而"什么算错"只能从真实失败里长出来——凭想象列出来的评分维度，写的通常是你**希望它做到什么**，而不是它**实际会怎么错**。这两件事的差距，就是均分漂亮、投诉照涨的差距。

四步的动作分别是：

1. **抽样 50–200 条**。要覆盖好、中、差三档，不能只抽失败样本——只抽失败的会高估问题比例，也会让分类法偏向极端个案。
2. **逐条读**。读输入、读输出、读轨迹。读的时候顺手记一件事：如果我是用户，这条我认不认？
3. **打标签**。给每条失败贴一到多个类别标签。标签怎么定，见 1.3。
4. **聚类、抽代表样本**。把标签归并成几大类，每类挑 2–3 条最有代表性的样本存下来。**这批样本就是 Golden Set 的第一批种子**——它的来源是真实失败，不是拍脑袋构造。

做完这一步，手上会有两样东西：**一份失败分类法**，和**一批带标注的代表样本**。注意它们都不是 prompt。

### 1.3 失败分类法：把"不好"变成可数的东西

以智能客服自动回复为例，这是第一轮错误分析可能得到的分类表：

| 类别 | 判定依据（可观察条件） | 代表样本 | 判分归属 |
|---|---|---|---|
| 意图理解 | 回复所解决的问题 ≠ 当前轮用户诉求 | 用户问退款进度，回复重述退款政策 | 模型 |
| 证据与检索 | 引用的政策条目不存在，或与知识库不一致 | 回复"7 天无理由"，实际政策是 15 天 | 断言 + 模型 |
| 推理链 | 多条款组合后的结论错误 | 首单 10/1 下单，回复"已过 15 天不可退" | 模型 |
| 格式与合规 | 必填字段缺失、取值越界 | 回复缺 order_id 与工单链接 | 断言 |
| 安全红线 | 承诺政策外的赔偿、泄露他人订单信息 | 回复"补偿 200 元"，政策无此条 | 双轨（见 §2.4） |

三个要点：

- **粒度要卡在中间**。太粗（"答得不好"）无法指导 rubric，太细（"第 3 句用了被动语态"）无法统计。一个可用的判据是：**每一类都能挑出代表样本**——挑不出来，说明这一类还没被真正看清。
- **判定依据写成可观察的条件，不写主观评语**。"意图跑偏"要落成"回复所解决的问题 ≠ 当前轮用户诉求"，它才能被复核、被交给别人标注。
- **占比是行动依据**。跑完第一轮，"哪一类占大头"就是你后面所有精力的分配去处。如果五成失败是必填字段缺失，那你要先写的是一批断言，而不是一个更复杂的 judge prompt。

这张分类表在系列里是公共坐标系：后面写 rubric（下一节之后）、按维度分层读一致性、设计抽检方案，都复用它。

### 1.4 顺序：分类法 → 尺子，不是反过来

值得强调一次：**先有分类法，再有评分标准。**

因为评分标准的每一个检查项，都应该能追溯到分类法里的某一类失败；追不上的检查项，就是在给不需要的能力加戏。

反过来先写 prompt，你就只能凭印象列出"我关心的维度"，最后得到的是一把与真实失败无关的尺子——这正是开篇那个均分漂亮、投诉照涨的来源。

## 二、判分边界：哪些检查根本不该交给模型

### 2.1 判据是"判定是否唯一"

有了失败分类法，下一步不是立刻上模型，而是把每一类失败分流：**这条检查，判定结果是不是唯一的？**

- **唯一 → 代码断言。** 格式合不合法、字段有没有、引用条目是否存在、数值在不在范围内——这些问题的答案不因人而异、不因模型而异，几行代码就能确定地判，没有理由交给一个概率模型去猜。
- **不唯一 → 模型代判。** 回答是否切题、结论是否被给定材料支持、语气是否得体——这类判断存在合理的分歧空间，正是裁判模型的价值所在。

这条边界最常被搞错的地方是**用难度当判据**。

"这条检查挺难的，让模型判吧"——难度不是理由，唯一性才是。反过来也成立："这个语义判断挺简单的，写个正则吧"——简单也不是理由，正则对语气和语义蕴含无能为力。

Arize 的表述更直接：能用代码断言的就别用模型（[来源](https://arize.com/guides/llm-as-a-judge/)）。

### 2.3 常见检查项的归属对照表

| 检查项 | 典型判据 | 归属 |
|---|---|---|
| 输出格式 / JSON 可解析 | 结构是否合法 | 断言 |
| 必填字段与枚举取值 | 字段存在 + 取值落在集合内 | 断言 |
| 长度 / 条数 / 数值范围 | 阈值比较 | 断言 |
| 引用的条目是否存在 | 与知识库做键匹配 | 断言 |
| 工具调用的返回值是否符合预期 | 退出码 / 状态码 | 断言 |
| 是否回答了用户**当前轮**的问题 | 语义对应关系 | 模型 |
| 结论是否被给定材料支持 | 语义蕴含 | 模型 |
| 语气是否得体、是否友好 | 主观评价 | 模型 |
| 是否泄露了他人信息 | 主体一致性可枚举 → 断言；措辞暗示 → 模型 | 双轨 |

这张表的用法是当模板：拿到一个新场景，先把检查项按这张表过一遍，能落到左边一栏的全部下沉为断言。

**断言越多，评测越便宜也越稳**——它们和模型打分不在同一个成本量级上（见 §4）。

### 2.4 灰色地带：可枚举就拆成断言集合

有些检查看起来"介于两者之间"，比如"安全合规"。处理规则是：**能把红线枚举出来，就拆成一组断言；枚举不完的部分，才进模型 + rubric。**

以客服场景为例，"不能承诺无依据赔偿"这条红线可以拆成两部分。

**可枚举的部分**：回复中是否出现政策条款外的金额数字、是否出现"我保证 / 一定赔付"这一类表述——交给断言。

**穷举不完的部分**："用模糊措辞暗示会赔偿"——交给模型判，并在评分标准里写清它依据什么判。

这里的取舍原则是**确定性优先**：能确定判的，就不要留给概率。

## 三、四种评分形态：判别力与成本的取舍

### 3.1 四种基础形态

Anthropic 在《Demystifying evals for AI agents》里给了一份 grader 分类学（[来源](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)），列出的手段有：代码断言、rubric 打分、自然语言断言、成对比较、参考物比对、多裁判共识。

工程上可以收敛成四种基础形态，另加一条聚合维度：

1. **程序断言**：跑脚本判定。成本极低、结果确定，不给"分数"只给通过 / 不通过。
2. **单点打分**：裁判读输入输出，按评分标准给一个绝对分（1–5 或 0–1）。最直观，也最容易失控。
3. **成对比较**：同时给裁判两个输出，问哪个更好。把"打几分"降级成"哪个更好"，判断难度大幅下降。
4. **参考物比对**：给裁判一份参考答案或范文，判断输出与它的关系（是否被支持、覆盖了哪些要点）。需要人工锚，但主观性显著低于单点打分。

第五种手段——多裁判共识与集成——不在形态层面而在聚合层面，属于另一个话题，后面单独展开。

### 3.2 判别力与成本矩阵

把四种形态放在同一张表里对比，取舍就清楚了：

| 形态 | 判别力 | 单次成本 | 能否给绝对质量 | 典型场域 |
|---|---|---|---|---|
| 程序断言 | 最高（判定唯一，零噪声） | 极低 | 不能，只有通过 / 不通过 | 格式、字段、红线、可执行结果 |
| 单点打分 | 中（易通胀、方差大） | 低 | 能，但绝对值不可信 | 日常监控、趋势观察 |
| 成对比较 | 高（相对判断，主观性最低） | 约为单条的 2 倍 | 不能 | 版本选择、模型对比 |
| 参考物比对 | 较高，但上限取决于参考物质量 | 中（要占上下文） | 能，且是相对参考物的质量 | 有标准答案或范文的场景 |

这张表里最容易被忽略的是**成对比较的"不能"**：它判别力最高、主观性最低，代价是无法回答"这条输出绝对质量如何"。

而很多团队恰好需要绝对值——比如监控"今天的回答质量比上周差了吗"。这时只能回到单点打分，但要接受它的不确定性，并靠其他手段补分辨力。

### 3.3 单点打分的病根是分数通胀

单点打分最常见的症状不是"分数忽高忽低"，而是**大量样本挤在 4/5 分**：均分 4.2、4.3，看起来不错，但 1–3 分档几乎没人。这种分布说明尺子的分辨力已经耗尽——合格与不合格的回答被折叠进了同一个区间。

这时候换一个"更严格的 prompt"治不了本。病根是没有定义失败（也就是本文主旨），而不是 prompt 不够狠。

三条可见的分辨手段：**把部分需求下沉为断言**（分层，见 §4）、**把绝对打分场景换成成对比较**（改形态）、**把评分标准拆到可判定**（下一节之后会专门讲）。

### 3.4 组合原则

一句话：**断言守红线，按标准打分做日常监控，成对比较做版本选择。**

落到具体问题上：

| 你要回答的问题 | 该用哪种形态 |
|---|---|
| 这次发版有没有踩红线、格式是否合规 | 程序断言 |
| 今天的整体质量比上周是好是坏 | 单点打分（只看趋势，不看绝对值） |
| A 版 prompt 和 B 版哪个更好 | 成对比较 |
| 输出是否覆盖了参考答案里的要点 | 参考物比对 + 要点枚举成断言 |

## 四、三层 eval 与运行节奏

### 4.1 三层各自判什么

Hamel 的三层 eval 结构（[来源](https://hamel.dev/blog/posts/evals/)）：

| 层 | 判什么 | 运行频率 | 谁负责 | 失败意味着 |
|---|---|---|---|---|
| Level 1：单测 / 断言 | 确定性断言（格式、字段、红线） | 每次提交 | 开发 | 代码缺陷，直接挡住 |
| Level 2：人工 + 模型评测 | 评分标准打分 + 人工抽检 | 每次发版 / 定期 | 评测 | 产品质量下降 |
| Level 3：A/B 实验 | 线上业务指标 | 有足够流量时 | 产品 | 业务价值未达成 |

三层不是"做得越多越好"的并列关系，而是**成本递增、频率递减**的串联关系。

### 4.2 节奏由成本决定

三层之间的关系可以画成这样：

<iframe class="j1-embed" src="/assets/html/judge-01/fig-3-eval-levels.html" title="三层 eval 的节奏" style="height:350px" loading="lazy"></iframe>

层与层之间的成本差着数量级，所以运行频率必须跟着成本走。把 Level 2 的模型评测塞进每次提交的 CI，结果通常是流水线变慢、人被逼着跳过它；只做 Level 1 的断言，则永远测不到主观质量。

节奏是成本算出来的，不是偏好定的。

这里也能看出 §2 那条边界的经济价值：**每一条能下沉为断言的检查，都从最贵的一层搬到了最便宜的一层**，而且顺带把噪声去掉了。

### 4.3 通过率是产品决策

Hamel 反复强调的一句话是：通过率不必是 100%，也几乎不可能是 100%。

原因在天花板上——MT-Bench 的研究里，人类评审员彼此之间的一致率也只有约 81%（[来源](https://arxiv.org/abs/2306.05685)）。要求裁判模型 100% 复现"标准答案"，这件事本身就不成立。

所以通过率该定成"当前基线，且不允许跌破"（也就是看趋势），而不是"必须满分"。

定成满分只有两个后果：要么尺子被放宽到什么都不算错，要么所有人开始想办法让分数好看——评测至此变成刷分游戏。门禁怎么设计、基线怎么抬，是后面的话题。

## 五、常见误区

1. **先写 prompt，再去找数据。** 顺序反了。第一版产物应该是失败分类法，不是打分模板。
2. **把"难判"当成"必须用模型判"。** 判据是唯一性。能写成断言的，无论写起来多费劲，都比交给模型可靠。
3. **用单一的 1–5 分覆盖所有需求。** 分数通胀之后，分数既无法区分质量，也无法归因问题。正确做法是分层：断言管确定的，打分管语义的，成对比较管版本。
4. **要求通过率 100%。** 参照物本身就有分歧，满分目标只会把尺子搞坏。
