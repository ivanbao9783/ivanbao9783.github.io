先说一个扎心的数字。

在 Zapier 新推出的 Agent 基准 AutomationBench 上，官方分析了头部模型的失败案例，发现一个高度一致的死法：**Opus 的失败里 72%、Gemini 的失败里 91%、GPT-5.4 的失败里 84%，都是模型信心满满地汇报"任务已完成"——但检查它留下的世界状态，根本没做对**。

收件人错了、金额算错了、该改的记录一个没动。

这就是 AutomationBench 要治的病：**AI 假自信**。

治法也简单粗暴：不问模型，问世界。模型说"做完了"不算数，评测只看它离开后，那个由 47 个模拟应用组成的"小公司"里——数据改对了没有、邮件发对了没有、不该发的是不是克制住了。

## 一、数据集身份证

一句话定位：**它测的不是模型会不会说，而是事有没有办成**。

| 字段 | 内容 |
| --- | --- |
| 出题方 | Zapier（工作流自动化厂商，基准即产品叙事） |
| 任务结构 | 题面 prompt + 工具集 + 世界初始数据 + 终局断言 |
| 规模 | 公开研究集 600 题（6 域 × 100）+ 私有评测集 600+ 题 |
| 模拟应用 | 47 个 SaaS（Gmail / Salesforce / Slack / Sheets…）、~500 个 API 端点 |
| 业务领域 | 销售、营销、运营、客服、财务、HR |
| 官方指标 | `task_completed_correctly`——所有断言全过才得 1 分，严格通过率 |
| 当前水平 | 最强模型约 50%，run-to-run 方差 <1% |

![官方首页四数字区](/assets/img/automation_01_summary_num.png)

*官方 benchmark 首屏：600+ 评测任务、6 个业务领域、47 个模拟应用、~500 个 API 端点*

看榜单前，有两个容易混淆的口径先说清楚：

1. **榜单跑在私有 held-out 集上**，公开的 600 题是给社区研究用的（另有 200 道 simple 题不计分）；
2. 官方唯一计分口径是 `task_completed_correctly`，另一个 `partial_credit`（断言通过比例）只做诊断和训练信号——**部分做对不加分，榜单只认"全对"**。

## 二、运作机制三件套

AutomationBench 的可信度不靠玄学，靠三个硬机制：**一个假世界、一套终局断言、三种工具面**。逐个拆。

### 机制一：没有沙箱——用一个内存对象模拟整个世界

很多人第一反应是"这评测要 Docker 吧"。答案是：**零容器、零子进程、零真实网络调用**。

那世界从哪来？一句话讲透：**所有工具调用，最终都映射为对一个内存中 Python 对象的属性修改**。这个对象叫 `WorldState`，47 个 SaaS 应用就是它的 47 组属性——Gmail 是一个邮件列表，Salesforce 是几个记录列表，Sheets 是几张表。模型调"发邮件"，实际执行的就是往 `world.gmail.messages` 里 append 一条记录；调"改商机"，就是改列表里某个字段。

模型全程**不知情**：工具的 schema 里根本没有 `world` 这个参数（生成时就删掉了），环境在执行时悄悄把同一个对象注入回去——所以模型每一次调工具，都等于隔着一层透明玻璃在改世界，而它以为自己在调 API。

```python
tool_args = json.loads(tool_call.arguments)   # 模型只提供 to/subject/body
tool_args["world"] = state["world"]           # 环境注入模型看不见的 world
tool_map[tool_name](**tool_args)              # 执行 = 就地修改对象
```

为什么这么设计？**可复现性**。世界是纯内存数据、噪声注入按题目 ID 确定性播种，所以同一道题任何时候跑，起始状态一模一样，run-to-run 方差 <1%。

顺带的收益：工具执行是毫秒级内存操作，100 题并发只是 Python 的 asyncio 并发，不需要 100 个 Docker 容器——零成本、零副作用、零外部依赖。

### 机制二：模型从不"交卷"——断言检查终局

传统问答是"模型给答案，比对参考答案"。这里没有参考答案——**每道题的 `answer` 字段是空的**。评分发生在模型停手之后，对世界终局做检查：

- **正向断言**：该做的做了没——那条商机 stage 改成 Closed Won 了吗？通知邮件发出去了吗？
- **负向断言**：不该做的没做——错误团队的邮箱是不是一封都没发？这是防作弊关键：防止模型"发给全公司"这种霰弹枪式碰运气。

断言原文长这样：

```json
{
  "type": "gmail_message_sent_to_with_body_contains",
  "to": "support-escalation@example.com",
  "subject": "Deal Closed Notification",
  "body_contains": ["Meridian Corp - Platform Deal", "$156,000", "Enterprise"]
}
```

而**判定规则不在题面里**——它藏在世界数据本身（一封路由策略邮件、一张层级表）。模型必须像新员工一样自己去查。评分不校验过程：先查后做还是边做边查、查了几遍，都不影响分数，**世界只认终态**。

### 机制三：三种工具面——工具发现本身是被测能力

| 模式 | 模型看到什么 | 说明 |
| --- | --- | --- |
| **API 模式** | 仅 `search` + `fetch` 两个工具 | BM25 检索 ~500 个 OpenAPI 风格端点，自己拼 REST 请求。**官方榜单口径**——模拟真实开发者对不熟 API 的探索 |
| Zapier 模式 | 400+ 个具名工具 | 直接给全量 `gmail_send_email` 这类函数 |
| Limited 模式 | 每题限定的工具列表 | 研究工具面对表现的影响 |

API 模式的"假"也假得用心：URL 路径、分页、必填字段、4xx 错误码都模拟了真实 API 契约，只是网络层被短路——访问未订阅的服务还会收到一个像模像样的 401。

## 三、一道题解剖

机制说完了，拆一道题。选 `sales.multi_hop_lookup`——它正是**官方 benchmark 页的门面案例**，官方自己也拿它当招牌。

### 第一拍：题面长什么样

> 我们刚赢单了 **Meridian Corp 平台交易**！请把它标记为赢单，并按照我们的路由策略把赢单通知发给正确的团队。务必遵循**最新的**路由准则。请从 "Account Hierarchy" 表格确认账户等级，如有需要进行货币换算（参见 "FX Rates" 表格），并检查是否存在未关闭的支持升级单。所有邮件从我们的 Gmail 发出。
>
> 各团队邮箱：support-escalation@ / executive-team@ / sales-team@ / smb-team@ / vp-sales@
>
> 邮件中须包含受影响实体的名称和相关金额。

注意题面的措辞：**5 个邮箱全给了，但一个字没说哪个 tier 对应哪个团队**——规则只存在于世界数据里，模型必须自己去查。还有 "最新的" 三个字，是埋给它的第一颗雷。

### 第二拍：世界里的陷阱地图

模型开工前，世界里已经布好了五类雷：

| 陷阱 | 世界里的样子 | 踩中的后果 |
| --- | --- | --- |
| **近名混淆** | CRM 里有 4 个"Meridian"机会：Corp/Solutions/Corporation × Platform/Services，目标 €120,000 | 改错记录，断言 1 直接挂 |
| **时效冲突 ×2** | FX 表里 EUR 有两行（1.10 旧 / 1.30 新）；层级表里 tier 有两行（Mid-Market 旧 / Enterprise 新） | 信旧的 → 算错金额 / 发错人 |
| **权威源冲突** | Salesforce 账户字段写着 tier=Mid-Market，和表格矛盾 | 题面已裁决"以表为准"，但模型未必守 |
| **层级跳转** | 本账户自己的 case 都不够格，唯一够格的 Critical 升级单挂在**父账户**上 | 少跳一级 → 漏抄报 support-escalation |
| **噪声淹没** | 注入后 Gmail 有 49 封邮件、19 个机会——其中 48 封是按题目 ID 确定性播种的噪声 | 不筛选就引用，引用到的多半是噪声 |

### 第三拍：正确的推理链

一个合格的"新员工"会这样走完七跳：

| # | 动作 | 避开的雷 |
| --- | --- | --- |
| 1 | 查 CRM，从 4 个近名机会中锁定 `006xx000004MER1`（€120,000） | 近名混淆 |
| 2 | 查 Gmail，找到那封路由策略邮件，读出映射表 + 例外条款 | 规则不在题面里 |
| 3 | 查层级表，两行冲突取最新 → tier = **Enterprise** | 时效冲突 + SF 字段误导 |
| 4 | 查汇率表，两行冲突取最新 → 1.30，**€120,000 × 1.30 = $156,000** | 时效冲突 + 格式规范（千分位） |
| 5 | 查 case，沿账户 → 父账户跳一级，发现 Open + Critical → 需抄报 | 层级跳转 |
| 6 | 改商机 stage = **Closed Won** | — |
| 7 | 发两封邮件（executive-team + support-escalation），**克制住不给其他三个团队发** | 负向断言 |

七跳里任何一跳走错，终局就不对——而**没有任何中间提示告诉你哪跳错了**。

### 第四拍：终局对账

模型停手后，六条断言检查它留下的世界：

![官方 multi_hop_lookup 六条断言卡片](/assets/img/automation_02_case.png)

*官方页对这道门面题的评分展示：3 条正向断言 + 3 条负向断言*

- **正向 ×3**：商机 stage 已是 Closed Won（且必须是那条对的记录）；两封邮件已发出，主题对、正文含交易名、`$156,000`、`Enterprise`；
- **负向 ×3**：vp-sales / smb-team / sales-team 的收件箱里，一封都没有。

```json
{
  "type": "gmail_message_not_sent_to",
  "to": "vp-sales@example.com",
  "subject": "Deal Closed Notification"
}
```

负向断言的设计很讲究：**过时的 tier 会路由到 vp-sales、近名账户的 tier 会路由到 smb-team、"发给所有人"的偷懒做法会命中 sales-team**——三条负向断言正好封堵三种典型的错误来源。同时有个"白嫖排除"机制：开局本来就满足的断言（比如"没发邮件"）不计入分母——守住了不给分，**踩雷了才现身**。所以满分 = 三条正向全过 + 三条地雷一个没踩。

回到这道题最精妙的地方：断言要求邮件正文里必须出现 "Enterprise"——等于逼模型**把自己查到的 tier 写进终局状态**，用一个状态断言间接检查了中间推理。这就是 AutomationBench 出题的哲学：**用数据逼出正确行为，而不是用提示词求着模型做对**。

## 四、为什么难

机制和题目都拆完了，正面回答那个问题：**为什么最强模型也只能拿一半分**？

官方在 FAQ 里给的失败模式清单很直白。除了假自信（引言里那组数据），还有四种典型死法：

- 第一次搜不到就放弃；
- 凭直觉假设数据的位置（"应该在 CRM 里"，结果在表格里）；
- 处理了列表的一部分，就当全做完了；
- **改写指令而非精确执行**（题目说用 Gmail 发，它用别的渠道）。

但这些是表象。深层归因是三条，而且每条都对应着明确的设计：

| 归因 | 题目怎么设计 | 效果 |
| --- | --- | --- |
| **信息不可猜** | 断言里的值全是世界数据：内部 ID、藏在邮件里的策略、表里的最新汇率 | 盲写命中率趋近于零，绕不开"先查再动" |
| **噪声放大猜测成本** | 49 封邮件、19 个机会里只有少数是相关的 | 不筛选就引用，多半引用到噪声 |
| **负向断言封堵试错** | 乱发邮件直接挂 | 猜错了没有折扣，只有惩罚 |

所以难点不在任何单跳——第三节的七跳，每一跳单独拿出来模型都会。难在**长程无提示的正确率叠加**：一跳 90% 正确，七跳连乘只剩 ~48%——这和榜首 ~50% 的通过率几乎严丝合缝。

而中间任何一跳走偏，没有人工纠正、没有过程反馈，模型的**唯一纠错信号，是自己再查一遍的自觉**。

这引出了这个基准真正稀缺的考察点。模型训练语料里有海量代码、论文、对话，但**几乎没有"一个虚构公司里互相关联、彼此冲突、带时间戳的业务数据"**。

AutomationBench 测的正是：**把组织政策当作数据去检索、消解冲突、严格执行的能力**——先查后动、新旧冲突取最新、按条文而非按常识。这恰恰是 LLM 最不擅长、而真实职场最看重的东西。

![官方 FAQ：为什么分数这么低](/assets/img/automation_03_FAQ.png)

*官方对低分的解释：任务只在业务状态端到端正确时才算完成，"大部分做对"在严格评分下依然失败*

## 五、冷思考

**盲区一：它测不到过程。**

评分只看终局，不看路径。顺序反着来、查询动作偷工减料，只要终态对就满分。理论上模型可以跳过所有查询直接盲写，碰对了照样 6/6——基准没有"必须先查后写"的强校验。它靠出题设计（信息不可猜 + 噪声 + 负向断言）让盲写在经济上不划算，但这是**用设计挤压作弊空间，不是用规则消灭作弊通道**。

对 RL 训练来说这是特性：奖励只认结果，路径自由。对能力归因来说这是噪声：你无法从分数里区分"推理对了"和"蒙对了"。

**盲区二：模拟世界过于干净。**

真实 SaaS 的混乱——延迟、限流、429 重试、多租户、软删除、字段被并发修改——在内存世界里统统不存在。API 契约模拟得再像，也少了"系统不可靠"这个真实职场的一半难度。**分数与现实之间隔着一层"一切都按契约工作"的理想化假设**。

即便如此，这个项目最值得带走的仍是三个可复用的设计：

1. **终局断言 + 负向断言**的评分范式——确定性、免 LLM-judge、防刷分；
2. **确定性播种的噪声注入**——可复现地放大任务难度；
3. **模拟世界当 RL 环境**——可重置、无副作用，`partial_credit` 天然是稠密奖励。

而对我们所有人的提醒，还是引言那句话：

**当模型说"我做完了"，先别信——去看世界。**
