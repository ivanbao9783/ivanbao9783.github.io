说一半的话，干五倍的活——这是 DeepSWE 给 agent 出题的方式。题面只有 SWE-bench Pro 一半长，参考解却重 5.5 倍。Datacurve 用 113 道原创题，治前沿模型的"挤团病"。

## 一、挤成一团的榜首

2026 年 9 月 3 日更新的 DeepSWE 官网榜单上，有个罕见画面：gpt-6-astra、gemini-3.8-flash、claude-opus-5，三家并列 74%。

分数打平，账单没打平——每题成本从 $2.36 到 $11.84，差 5 倍。

并列不是巧合，是饱和的症状。今天的公开编码基准上，前沿模型挤在一个窄带里，置信区间互相重叠，榜单越来越像礼貌性的合影。

DeepSWE 就是来拆台的：113 道原创工程题，让同一批模型拉开 69.8 分的带宽。在 SWE-Bench Pro 上，它们的差距只有 29.7 分。

![官网榜单 Top10](/assets/img/deepswe_01_leaderboard_top10.png)

*图 1｜来源：deepswe.datacurve.ai/leaderboard，2026-09-03 版（Top10 区域）。一图交代三件事：榜首三家并列 74%、每题成本差 5 倍、长尾衰减到 36%*

怎么做到的？两个字：换题。准确说，是连出题和判卷的方式一起换。

## 二、身份卡

- 出品：Datacurve（论文 arXiv:2607.07946，2026-07）
- 规模：113 道任务，横跨 91 个活跃开源仓库、5 门语言（TypeScript / Go / Python / JavaScript / Rust）
- 题目：全部从零原创，永不合并回上游
- 判卷：每题一份手写功能 verifier，不是继承 PR 的测试
- 跑法：所有模型统一跑 mini-swe-agent——同一把 bash 工具、同一份系统提示词
- 格式：Harbor 任务格式；跑分引擎是 Pier（Harbor fork，加了 per-agent 网络白名单），榜单跑在 Modal 上
- 指标：pass@1（按题宏平均）+ pass@4（四次抽样至少一过）

口径说明：本文官方数据（官网/榜单）截至 2026-09-03；论文数据为 arXiv v1 固定版本。

## 三、出题：让参考解从没上过网

SWE-bench 范式是从已合并的 PR 里挖题。这有两个结构性隐患。

一是预训练污染：题面、修复代码、讨论贴早就在公网上，模型可能背过答案。有研究实测过：SOTA 模型在基准内复现金标解的比率显著高于基准外——高分可能只是记性好。

二是包装泄漏：金标 commit 就躺在评测容器的 .git 历史里。外部报告统计过 SWE-Bench Pro 上的 38 起作弊 trial，33 起（87%）是直接从 .git 历史里把答案翻出来的。

DeepSWE 的应对很直接：题目从零写，参考解从零写，并且永不回传上游仓库。你没法背一道从没上过网的题。

题库覆盖也有讲究：仓库准入要 ≥500 星、活跃维护、宽松开源 license；91 个仓库的中位数只贡献 1 道题——不给任何单一代码库垄断榜单的机会。

![语料统计对比](/assets/img/deepswe_02_corpus_stats.png)

*图 2｜来源：论文 arXiv:2607.07946v1 Figure 2（三基准语料统计对比）。一张图说清"说一半的话，干五倍的活"：prompt 长度约 SWE-Bench Pro 一半，参考解触碰代码 5.5×、文件数更多*

代价是明摆着的：每道题都要真人工程师端到端写出题面、参考解、verifier，再过四维人工评审。113 道，全是手工活。

## 四、判卷：1.4% vs 32.4%

题好只是半个基准，另半个是判卷。

继承式判卷（拿 PR 自带的测试当评分标准）有个老问题：那些测试是为了确认某一次特定修复写的，不是为 grading 任意未来提交写的。合理的替代实现可能被误杀，取巧的半成品可能被放过。

DeepSWE 每题手写功能 verifier：只测题面声明的行为，走公共 API 和可观测输出，不查内部符号名——任何给出正确行为的实现都算过。

硬数字来自一次独立审计：每个基准抽 30 题 × 9 配置 × 3 次运行，GPT-5.5 当 judge 逐条复审。judge 与 DeepSWE verifier 的分歧率：**1.4%**。与 SWE-Bench Pro 继承测试的分歧率：**32.4%**。

![verifier 宽容度审计](/assets/img/deepswe_03_verifier_audit.png)

*图 3｜来源：论文 arXiv:2607.07946v1 Figure 5（Verifier permissivity，n=789 vs 735 rollouts）。诚实备注：1.4% 建立在个位数事件上（2 FP + 8 FN），区间 [0.7, 2.5]%；但与 [29.2, 35.8]% 相距甚远，差距本身是稳的*

判分环境是另一道防线。v1.1 起，agent 和 verifier 分容器：agent 在无网沙箱里干活、commit；collect hook 把 diff 抽成 patch，接力到一个干净重建的判分容器——**test.patch 判分时才注入，agent 全程不可见**。

![双容器判分管线](/assets/img/deepswe_04_pipeline.png)

*图 4｜自绘（Excalidraw 手绘风，.excalidraw 源文件随文预埋）。Agent 容器（无网 · 3h）：agent 只拿题面，bash 探索/编辑/自测后 commit。判分容器（干净重建）：collect hook 抽取 git diff → model.patch，干净重放 base commit，判分时才注入 test.patch，test.sh 跑 21 个 Challenge 测试，输出二元 reward*

verifier 自身还有三道质检：作者期连跑三次，结果不稳的打回（防 flaky）；每次判分附回归检查——改对了需求但弄坏了别处，照样挂；上线前过四维人工评审（prompt-verifier 双射、接受广度、真实性、环境洁净）。

## 五、单题深挖：abs-module-cache-flags

看一道具体的题。仓库目录第一题，目标仓库是 abs-lang/abs（一门 Go 写的脚本语言），类别 enhancement。

题面约 2000 字符，五组需求，我直译其骨架：

1. **模块解析与缓存**：等价路径复用同一缓存条目；裸模块名（如 `demo`）解析为 `demo/index.abs`；查找顺序：当前目录优先，再按序列走 `ABS_MODULE_PATH`
2. **缓存可见性**：暴露 `require_cache_info()`（hits/misses/size/inflight）、`require_cache_keys()`、`reset_require_cache()`
3. **循环导入**：报错必须以 `cyclic module import detected:` 开头，且带上环链
4. **调试追踪**：`ABS_MODULE_DEBUG` 或 `--module-debug` 触发，输出到运行时 stderr
5. **CLI 脚本模式**：`--module-path` / `--module-debug` 在脚本模式生效；未知 flag 不得阻断脚本路径检测

题面最后两行是灵魂：内部函数名、签名、文件布局，**都是实现细节**。

这就是"说一半的话"的现场：题面只约定行为，不约定形状。agent 得自己读一个陌生代码库，找到模块加载在哪实现的，自己决定改动怎么组织——通常还是多文件的。

判卷侧，verifier 是 21 个 Challenge 测试（evaluator 15 + repl 6），与题面五组需求可以逐条对账：

| 题面需求组 | 对应 Challenge 测试 | 数量 |
| --- | --- | --- |
| 1 模块解析与缓存 | RequireCanonicalPathCaching、RequireBaseDirPrecedenceOverModulePath、RequireModulePathQuotedEntries、RequireModulePathQuotedRelativeCanonicalDedup、RequireModulePathFirstEntryPrecedence、RequireModulePathResolutionAndCacheStats、RequireOSEnvFallback、RequireRuntimeEnvPrecedenceOverOSEnvForModulePath | 8 |
| 2 缓存可见性与重置 | RequireCacheKeysSorted、RequireCacheKeysCanonicalAbsolutePaths、RequireResetRequireCacheClearsState | 3 |
| 3 循环导入 | RequireCycleDetection | 1 |
| 4 调试追踪 | RequireDebugTraceOutput、RequireDebugWritesToRuntimeStderr、RequireRuntimeEnvPrecedenceOverOSEnvForDebug | 3 |
| 5 CLI 脚本模式 | BeginReplSignature、BeginReplScriptModeWithModulePathFlag、BeginReplScriptModeWithOSEnvFallback、BeginReplScriptModeWithModuleDebugFlag、BeginReplScriptModeWithDoubleDashScriptPath、BeginReplScriptModeWithUnknownFlagBeforeScript | 6 |

对账表两侧严格咬合：题面立下的每组需求都有测试接住，测试断言的行为题面都有出处——但没有一条测试检查函数名、签名或文件布局。

有意思的是作弊信号的处置：verifier 会扫描 vendored 依赖、TestMain 劫持、越界路径改动——**只记录，不拦截**。哪怕你用了很怪的手段，只要行为对就过；记录留给人类复核。

## 六、失败模式：谁在栽跟头

论文的轨迹分析（judge 逐条标注 verdict）给了几个反差结论。

Claude 系最常栽在"枚举式需求"上：题面说 sync 和 async 都要支持，Claude 实现了 sync，忘了给 async 镜像。约三分之二的 MISSED_REQUIREMENT 都是这种"只发了一个分支"。

GPT 系最守需求：漏需求比率全场最低，且多次尝试同一题会收敛到同一理解——像性格，不像波动。

自验证行为也分化：强模型（Opus 4.7、GPT-5.4）在 80% 以上的运行里自己写测试；Gemini 3 Flash 有 18% 的运行零测试裸提交。

![自验证行为对比](/assets/img/deepswe_05_self_verification.png)

*图 5｜来源：论文 arXiv:2607.07946v1 Figure 10（自验证哑铃图：同一 agent 在 DeepSWE vs SWE-Bench Pro 上自写测试的频率）*

最扎心的对照：同一个 agent，在 SWE-Bench Pro 上自写测试的频率骤降——因为 SWE-bench 的题面包装语告诉它"测试我们已经处理了，别动测试逻辑"。一句提示词，就改掉了 agent 的行为。**基准的设计，本身就在塑造被测者的行为。**

## 七、批判：它自己承认的边界

这个基准不是银弹，论文 §8 自己列了一串：

- **二元奖励，无部分分**。差一个需求的实现和完全跑不通的，得分一样
- **只测功能正确性**。可读性、可维护性、性能一概不测。过了 verifier 不等于 maintainer 会 merge
- **单一 harness**。统一 mini-swe-agent 换来了可比性，但绕开了各家原生编辑工具——测的是模型，不是产品
- **审计的小字**。1.4% 是个位数事件上的比率；judge 是 GPT-5.5，恰好是论文榜第一名，自偏好嫌疑无法排除
- **污染只是被推迟**。题一发布，就开始进下一次训练。官方的答案是持续补充新题——手工活的成本没有消失，只是被摊平

## 八、可带走的设计

如果只从 DeepSWE 带走三样东西：

1. **原创题 + 永不回传**，是比追着模型截止日期跑更省心的防污染姿势
2. **手写功能 verifier（只测行为不测形状）+ 双容器判分（test.patch 判分时注入）**，这套组合可以整体迁移到任何自建评测
3. **把判分诚实度写进口径**：作弊信号记录不拦截；agent 可控的失败（超时、上下文耗尽）计为失败，基础设施故障不计分
