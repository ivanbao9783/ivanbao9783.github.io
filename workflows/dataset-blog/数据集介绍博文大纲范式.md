# 数据集介绍博文大纲范式（可泛化）

> 用途：介绍一个 AI/Agent 数据集或基准时，套用本范式快速生成知乎/掘金风格的技术博文大纲，并按第九节规范集成到本站（ivanbao.github.io）发布。
> 产出实例（线上博文，可对照参考）：
> - AutomationBench（业务模拟型）：https://ivanbao9783.github.io/posts/automation-bench/
> - ALE（真实环境交付型）：https://ivanbao9783.github.io/posts/ale-agents-last-exam/
> - DeepSWE（代码真实仓库型）：https://ivanbao9783.github.io/posts/deepswe/

## 一、命名规则（硬性）

1. **标题必须含数据集名**——读者扫一眼列表就知道"这是讲哪个数据集的"
2. 标题副结构推荐公式：`数据集名 + 深度拆解/解读 + 一句反差钩子`
   - 反差钩子来源：出题方身份（如"Zapier 用 47 个假应用"）、能力反差（"最强模型也只有 50 分"）、机制反差（"模型说自己做完了，世界说没有"）
3. 一篇一个 hook，不要堆叠

## 二、六层结构（按出现顺序）

### 第 ① 层 · 冷启动锚点（Hook）—— 250 字

- **功能**：用反直觉数据/事实制造信息差，回答"为什么要读这篇"
- **素材来源优先级**：官方披露的失败模式数据 > SOTA 分数反差 > 出题方身份 > 规模数字
- **禁忌**：不念定义、不讲背景、不放目录

### 第 ② 层 · 身份卡（What）—— 400 字

- **功能**：30 秒建立坐标系——谁出的、测什么、多大、什么口径
- **必备字段**：出题方 / 领域与规模 / 任务单元结构 / 官方指标 / 当前 SOTA 水平
- **形式**：一张字段表 + 一句话定位
- **资产**：官方规模数字区 / 论文题目构成图（如全池分布图）的紧凑截图（可信度最高）
- **口径声明**：正文开头（身份卡内）统一声明本文官方数据（官网/榜单）的截取时间；论文数据为固定版本，无需逐处标注

### 第 ③ 层 · 机制拆解（How）—— 1,000 字

- **功能**：回答"它凭什么可信 / 可复现 / 防作弊"——数据集介绍文的差异化主力，区别于新闻稿
- **写法**：找出数据集的 2-4 个核心机制，每个一小节，**论断 + 证据（代码/数据原文），不留展开叙述**
- **资产**：一张端到端流程图（灵魂图）+ 关键代码块 2 个以内；论文已有管线/架构图时**直接截论文 Figure 复用**（含编号与图题），不重画 mermaid/Excalidraw
- **注意**：机制数量与篇幅成反比，选最独特的，不选最正确的

### 第 ④ 层 · 单题深挖（Case Study）—— 1,300 字（全文最重）

- **功能**：信任的具象化——读者从"理解"落到"信服"
- **选题标准**：官方门面案例（若有）> 含最多陷阱的中等难度题 > 最难题
- **四拍结构**：题面原文（中译）→ 陷阱地图 → 正确推理链（表格化）→ 评分对账
- **信任三角**：一图一表一断言（流程图/推理链表/评分原文）——三样齐，读者就信
- **优先级说明**：本层与第 ③ 层是全文支柱，压缩字数时最后砍这两节

### 第 ⑤ 层 · 难度归因（Why Hard）—— 550 字

- **功能**：从"是什么"升到"为什么"——无此层文章沦为说明书，有此层文章有观点
- **归因来源**：官方披露的失败模式 > 出题设计的经济学（防作弊/防猜测机制）> 与训练数据分布的差异
- **形式**：失败模式 × 题目设计对照表（每种失败谁封堵它）

### 第 ⑥ 层 · 批判性收尾（So What）—— 600 字

- **功能**：保质期——纯吹的文章三周被遗忘，有独立判断的文章被收藏
- **三段式**：它测不到的（盲区）→ 它的边界（模拟 vs 现实的 gap）→ 它最值得带走的可复用设计
- **资产**：官方榜单现状截图（紧凑裁剪，可上移至第 ② 层）
- **可选件（默认不加）**：与相邻基准的范式对比表、金句式收尾——宏大叙事和口号会稀释批判段的密度；确要放对比表，只作为批判段内的论据

**独立解耦原则（全篇硬约束）**：每篇数据集介绍文自成一体，**不在正文中凭空引入与其他数据集的横向对比**。只有两种情况例外：① 官方素材本身含对比（论文/榜单/FAQ 明确给出）；② 用户在输入里明确要求对比。本篇讲不清的，留给下一篇讲。

## 三、泛化边界：通用骨架 vs 数据集类型专有件

范式分两层：**骨架层**换任何 Agent 数据集都直接成立；**专有件层**随数据集类型整体替换。写新数据集前先判类型，再换件。

### 骨架层（通用，直接套用）

六层结构本身、各层功能定位、字数占比、资产策略（官方素材背书 + 论文原图优先 + 截图位预埋）、压缩优先级、平台适配、校准清单——全部与数据集内容无关，属于"任何 Agent 数据集介绍文"的公共骨架。

### 专有件层（随数据集类型替换）

以三大类型对照（AutomationBench = 业务模拟型；DeepSWE = 代码真实仓库型；ALE = 真实环境交付型）：

| 范式位置 | 业务模拟型实例（AutomationBench） | 代码仓库型泛化示例（DeepSWE 类） | 真实环境交付型实例（ALE） |
| --- | --- | --- | --- |
| ③ 核心机制 | 内存 WorldState / 终局断言 / world 隐藏注入 / 噪声确定性播种 | 沙箱隔离（Docker）/ fail-to-pass 测试验证 / 补丁应用与环境搭建 | 真实 VM + 专业软件 / hidden reference 停手后注入 / gate-and-score 且默认禁 LLM-judge / 真实项目过五道 QC 门 |
| ③ 灵魂图 | world 读写分离 + 断言绕开模型视野 | 沙箱生命周期 + patch 接力 + 测试裁决 | main.py 三生命周期 + agent 动作循环 + VM 四目录契约（**论文已有 Figure 6，直接截原图**） |
| ② 任务单元结构 | prompt + 工具集 + 世界初始数据 + 终局断言 | issue 原文 + 仓库快照 + 测试用例 | 可执行 main.py（load/start/evaluate）+ input/ 任务数据 + reference/ 隐藏参考 |
| ④ 题面原文 | 业务任务 + 团队邮箱列表 | GitHub issue 原文（含歧义与隐含需求） | 专家真实项目的完整工作流指令（如 ERP 供应链 12 阶段流程） |
| ④ 陷阱地图 | 近名混淆 / 时效冲突 / 权威源冲突 / 层级跳转 | issue 措辞歧义 / 环境依赖缺失 / 隐含需求 / 相关测试噪音 | 链式硬依赖 / 路由分流 / 精确数字容差 / 序列号纪律 / 防作弊标签（run tag） |
| ④ 评分对账 | 正负向断言逐条过（6/6） | fail-to-pass 测试全绿 + pass-to-pass 不回归 + 需求组↔测试对账表（题面每组需求都有测试接住，逐条对账） | 硬门全过（任一触发即 0 分）+ 等权 checks 逐项对账（如 3 门 + 12 checks） |
| ⑤ 失败模式 | 假自信汇报完成 / 霰弹枪式试错 | 补丁过拟合 / 只改测试不改实现 / 环境误判 | 领域知识缺位退回 ad-hoc 脚本 / 策略错误 / 长程提前放弃（Approach 47% > Understanding 31% > Execution 22%） |
| ⑥ 批判盲区 | 模拟世界太干净（无限流/并发）/ 只测终态不测过程 | 沙箱与真实 CI 的 gap / 测试覆盖不足即漏网 | 只考终局产物不看过程 / 少数视觉 probe 仍主观 / 复现门槛高（每题数美元×数小时）、公开子集代表性存疑 |

### 判别方法（写新数据集时逐项问）

1. **评测对象是什么**——业务状态（模拟世界型）、代码行为（真实仓库型）还是真实软件环境里的交付物（真实环境交付型）？决定第 ③ 层机制和灵魂图的来源（自绘 or 截论文原图）
2. **裁决靠什么**——状态断言还是测试执行？决定第 ④ 拍"评分对账"和信任三角里的"一断言"长什么样
3. **题目从哪来**——人工构造还是真实世界挖取（issue/PR）？决定陷阱地图的来源和第 ⑤ 层归因的角度
4. **跑一题的物理成本**——毫秒级内存操作、分钟级沙箱启动还是数美元×数小时的真机运行？影响身份卡"成本"字段和第 ⑤ 层的难度经济学

## 四、字数与节奏基准（目标阅读时长 15–20 分钟，约 4,000–4,500 字）

> **节奏硬约束：语言精炼，行文要有呼吸感**——短句为主、一段不超过 5 行、每个机制小节之间留白呼吸；宁可删得狠，不可写得满。阅读时长以 4,000–4,500 字 + 4–5 张图估算，超了按第六节压缩优先级砍。

| 层 | 占比 | 说明 |
| --- | --- | --- |
| ① Hook | ~6% | 越短越有冲击力 |
| ② 身份卡 | ~11% | 表格承载，文字极少 |
| ③ 机制拆解 | ~25% | 支柱之一 |
| ④ 单题深挖 | ~31% | 支柱之二，全文最重 |
| ⑤ 难度归因 | ~13% | 观点密度最高 |
| ⑥ 批判收尾 | ~14% | 不可砍 |
| 合计 | 100% | — |

## 五、资产策略

1. **每篇 4–5 张图（数量硬指标）**：图不足 4 张时必须自绘补齐——长文无图读不动，4 张是可读性下限，5 张封顶防注水
2. **可信度资产优先官方**：leaderboard、官方统计区、论文原图——数据集介绍文的公信力主要靠官方素材背书
3. **一张图只承载一个信息单元，紧凑裁剪**：每个截图位必须写明"来源页面 + 截什么、不截什么"（如 leaderboard 只截 Top10 图表区，不带导航和明细表；统计区不带合作伙伴墙）；**禁止整页大截图**
4. **架构图优先复用论文原图**：论文已有管线/架构图时直接截 Figure（含编号图题）
5. **自绘两段式流程（官方无图时兜底）**：
   - **第一步·mermaid 概念稿**：先用 mermaid 画草图（数据流/模块关系），交用户确认——改 mermaid 源码比改成品图快一个量级，概念对不上就不进入下一步
   - **第二步·Excalidraw 终稿**：概念确认后再用 Excalidraw 画正式图（手绘风格、圆角、与站内其他博文图风一致），**只预埋 .excalidraw 文件引用，不导出 PNG**——与其他截图一样走「预埋 → 用户统一导出/补录」流程；**终稿生成后必查元素文字居中、完整展示**（常见缺陷：绑定文本不居中/溢出截断），导入画布肉眼核验后再定稿
6. **截图位只预埋、不代截**：写作时标注（📸 + 编号 + 来源 + 裁剪范围 + 图注），由作者统一截图补录

## 六、压缩优先级（当字数超预算时，按此顺序砍）

1. 先砍第 ② 层的领域逐一介绍（改一句话列举）
2. 再压缩第 ③ 层各机制的展开叙述（保论断和证据）
3. 再压缩第 ⑤ 层的失败模式列举（改一行引用）
4. **最后才动第 ④ 层和各节的核心观点句**——它们是文章的不可替代性所在

## 七、平台适配（知乎首发 → 掘金同步）

- **知乎**：小标题分节、图表丰富（紧凑截图 + 论文原图）、观点句加粗
- **掘金同步版**：代码块可适当加回（第 ③ 层允许 3-4 个）、标题可去掉钩子改直述、加 TL;DR 段
- 同步不改结构，只调密度

## 八、写作前置校准清单（动笔前逐项确认）

- [ ] 私有集与公开集的规模和用途分清了吗
- [ ] 官方榜单口径（哪个指标、哪个模式）写对了吗
- [ ] 正文开头统一声明官方数据（官网/榜单）的截取时间了吗（论文数据为固定版本，无需逐处标注）
- [ ] 榜单是 SPA 页面时，找过底层数据端点（如 /api/xxx/leaderboard）吗——原始数据比截图准
- [ ] 引用的失败模式数据有官方出处吗
- [ ] 选的 case 是官方门面案例吗（若不是，为什么选它）
- [ ] 每个机制小节有"论断 + 证据"两件套吗
- [ ] 批判收尾有至少一个别人没说过的观点吗
- [ ] 数据集类型判对了吗（模拟世界型 / 真实仓库型），第三节对照表里的专有件换对了吗
- [ ] 每个截图位写清"来源 + 截什么、不截什么"了吗（无整页大截图）
- [ ] 图够 4–5 张了吗（不足 4 张按第五节自绘两段式流程补齐；自绘图先过 mermaid 概念确认）
- [ ] Excalidraw 自绘图的元素文字居中且完整展示吗（无溢出/截断）
- [ ] 架构图优先复用论文原图了吗（论文有图就不自绘）
- [ ] 正文中没有凭空引入其他数据集的横向对比吧（官方素材或用户要求除外——独立解耦原则）
- [ ] 朗读一遍有呼吸感吗（短句、段落 ≤5 行、无堆砌长句）；预计阅读时长在 15–20 分钟内吗
- [ ] 结尾默认停在批判 + 可带走设计上，没加时代位置对比表和口号式金句吗

## 九、仓库集成规范（发布到本站时的硬性要求）

博文成文后要发布到本站（ivanbao.github.io，Jekyll + Chirpy + 知识星图），必须完成以下四件套。缺任何一件，博文就不进星图聚合、反链缺失或图片 404。

### 9.1 文件与 front matter

- 文件名：`_posts/YYYY-MM-DD-<数据集名 slug>.md`（日期=实际发布日；slug 小写连字符，如 `ale-agents-last-exam`）
- front matter 模板：

```yaml
---
title: "<完整标题，含数据集名与钩子>"
author: ivanbao9783
date: YYYY-MM-DD HH:MM:SS +0800
categories: [数据集]
tags: [数据集, <数据集名>, Agent 评测, 基准]
description: <一句话摘要，含数据集名与最强反差数字>
---
```

- 正文首行不再写 `# 标题`（front matter 已含，重复会出现双标题）

### 9.2 图片资产

- 存放：`assets/img/<文章slug>/`（每篇文章的图片资源归自己的目录），命名 `<数据集前缀>_<序号>_<说明>.png`（如 `ale_02_leardboard.png`）；`.excalidraw` 源文件随 PNG 同目录存放
- 引用：**站内根绝对路径** `/assets/img/<文章slug>/<文件名>`（本地 markdown 预览器不解析属已知问题，以 `jekyll serve` / 线上为准）；文件名**不含空格**（空格需 URL 编码，易出错）
- 图注转正：写作期的「📸 预埋 N」在补图后转为正式图注——`*图 N｜来源：<出处与版本>。<口径备注>**`；截图操作指令（"只截 / 不要截"）删除，**口径备注必须保留**
- **图注禁 AI 痕迹（硬性检查项）**：图注只写来源与口径备注，不写元叙述——"一张图说清……"、"一图交代三件事"、"自绘（Excalidraw 手绘风……）"、"诚实备注："之类的解说式引子一律删除；口径说明直接陈述（如"1.4% 建立在个位数事件上……"），不加标签前缀

### 9.3 星图登记（starmap.yml）

- 数据集介绍类博文登记到 `dataset` 星团对应节点的 `posts:` 列表（默认 `corpus` 开源数据集全景；讲数据构造方法的进 `construction`；讲压缩/蒸馏的进 `compression`）
- 追加一行文件名即可，**不改博文 front matter**（分类反链由站点 hook 自动注入）
- 登记后该节点博文数自动 +1，落地页与星图节点大小随之更新

### 9.4 集成自检（push 前逐项过）

- [ ] front matter 三必需（title/date/tags 含「数据集」）齐全
- [ ] 正文所有图片引用与 `assets/img/<文章slug>/` 实际文件一一对应（可 grep `](/assets/img/` 与目录 diff）
- [ ] 无「📸」残留（预埋位全部转正或删除）
- [ ] starmap.yml 已登记且 YAML 可解析
- [ ] push 后 CI success + 线上抽查：博文 200、图片 200、落地页聚合数 +1、博文文末出现「所属领域」反链
