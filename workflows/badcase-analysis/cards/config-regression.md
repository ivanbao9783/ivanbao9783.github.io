# 模式卡 · 配置退化型（Config Regression）

> 类型 ID：`config-regression` · 常见严重度：P1 · 判定基准：分数随配置变化，且可归因到配置引发的**行为改变**（而非采样噪声）。

## 1. 识别特征

- 同一模型、同一数据集，**仅更换配置**（推理档 `effort` / 温度 / 工具集 / 预算上限）后，某类任务分数下降。
- 高危形态：**整体分数上升，但特定域 / 任务类型逆势下降**——聚合分数掩盖退化。
- 常伴副作用：撞步数上限任务数上升、Token 用量膨胀。

## 2. 判定基准（准入条件）

同时满足：
1. 分数差异可复现（同一配置重跑仍现退化倾向），非单次抖动；
2. 能定位到配置引发的**行为风格变化**（如并行 → 串行、探索 → 保守）；
3. 排除了数据集变更、harness 版本变更等其他变量。

## 3. 现场还原要点（M1）

该模式的现场还原核心是**同任务跨配置对照**，抓以下证据：

| 观测面 | 抓什么 | 说明 |
|---|---|---|
| 调用密度 | 轮次 / 工具调用总数 / 调用每轮 | **总调用数变化不大但轮次显著增加 = 串行化指纹** |
| 预算消耗 | 步数 / 上限、撞限任务增量 | 区分"变弱"与"预算被提前耗尽" |
| 终态快照 | 失败任务最后一条动作 | 停在"读取/验证"而非"执行/提交" = 验证截断 |
| Token | 输入 / 输出 token 变化比 | 输出膨胀常是串行验证的副产品 |
| 域级下钻 | 按域 / 任务类型拆 PASS→FAIL 翻转 | 禁止只看总分 |

## 4. 核心资产抽取清单（M2）

- **调用密度对比表**（同任务 default vs 新配置）
- **PASS↔FAIL 翻转清单**（分域、分任务类型）
- **撞限增量**（新增撞限任务数 − 逃离数）
- **Token 膨胀比**
- **任务形态-敏感度映射**（哪类任务对配置敏感）

## 5. 归因指纹（M3）

典型层级分布：**模型层（行为风格改变）> harness 层（预算刚性）> 数据层（任务形态）> 采样层（噪声）**。

- 模型层：配置提升改变了操作风格（并行→串行），单位工作量轮次膨胀；
- harness 层：固定的步数上限把串行化放大成预算耗尽；
- 数据层：链长、跨多应用的任务对轮次消耗天然敏感。

## 6. 修复动作（三侧）

- **数据集侧**：为任务标注"最小可行步数 / 预算敏感度"；对长任务补过程中间断言。
- **模型侧**：提示层鼓励"无数据依赖的调用同轮并行发起" + 预算感知（先提交副作用动作、后验证）。
- **harness 侧**：按任务类型设差异化步数上限，或引入"步数-完成度"软约束（临近上限提示收尾）。

## 7. 证据锚点（融合自案例）

- 推理档退化案例：default→max 整体 +3.5pp，但 sales 域 44%→40%、撞限 9→19；`docusign_contract_send` 总调用数 162→111 而轮次 42→50（串行化铁证）。→ [博文](/posts/automationbench-effort-regression/) · `tmp_workspace/badcase-blog/automationbench_effort_regression.md`

## 8. 关联模式（多标签）

- **结构性预算型**：配置引发的撞限即该模式的一种成因（次模式）。
- **全有全无翻转型**：配置扰动叠加贴边任务可诱发二值翻转。
